# Проверка до списания и кабинет аналитика

Payment Core теперь вызывает платформу перед переводом, выводом и списанием резерва. Без работающей платформы и `PIP_CORE_TOKEN` новые списания получают `503 RISK_UNAVAILABLE`. Отключателя проверки и автоматического разрешения при сбое нет. Пополнения, возвраты, создание, отмена и истечение резервов сохраняют прежнее поведение.

## Локальный запуск

1. Подготовьте БД обоих проектов по их README. В платформе выполните `scripts/init-integration.ps1`. Для ранее созданного `.env.integration` выполните `scripts/init-analyst.ps1`: он добавит только отсутствующий `PIP_ANALYST_TOKEN`, сохранив существующие значения. Секреты не выводятся и не передаются браузеру.
2. Запустите платформу с JDK 21 и профилем `local-lite`. Она автоматически читает `.env` и `.env.integration`.
3. В терминале **Java-ядра** передайте дополнительный файл и включите доставку событий:

```powershell
$env:JAVA_HOME='C:\Program Files\Java\jdk-21.0.12.1'
$env:PATH=$env:JAVA_HOME+'\bin;'+$env:PATH
$env:SPRING_CONFIG_ADDITIONAL_LOCATION='optional:file:C:/Users/ww/Documents/Codex/payment-intelligence-platform/.env.integration[.properties]'
$env:PAYMENT_INTELLIGENCE_DELIVERY_ENABLED='true'
.\gradlew.bat --no-daemon bootRun --args="--spring.profiles.active=local"
```

Путь зависит от компьютера. Backend платформы остаётся на 8081, ядро — на 8080, БД платформы — на 5435. По умолчанию ядро использует `http://127.0.0.1:8081/internal/v1/risk/evaluations` для риска и `http://127.0.0.1:8081` для шлюза. Параметры для другого локального порта: `PAYMENT_INTELLIGENCE_RISK_URL` и `PAYMENT_INTELLIGENCE_PLATFORM_URL`.

4. Войдите существующим ADMIN в [Payment Core](http://127.0.0.1:8080/). В меню выберите «Кабинет аналитика» или откройте [кабинет](http://127.0.0.1:8080/intelligence/). UI и API идут через тот же origin и ту же сессию. Предварительно пересоберите JAR ядра, если запускаете готовый архив. При `bootRun` ресурсы панели ядра собираются его стандартной Gradle-задачей.

Платформа должна обслуживать собранный UI: используйте её JAR после `gradlew.bat build`. При backend-разработке через `bootRun` собранные ресурсы можно подключить параметром `--spring.web.resources.static-locations=file:./web/dist/` после `npm run build` в `web`. Кабинет через шлюз проверяется на собранных JAR. Vite используется для разработки UI и браузерных тестов; отдельная браузерная авторизация платформы не создаётся.

`PIP_CORE_TOKEN` даёт только доставку событий и оценку риска, `PIP_EXPORT_TOKEN` — экспорт ядра, `PIP_ANALYST_TOKEN` — API аналитика через шлюз. Секрет аналитика должен отличаться от секрета риска. Старый ADMIN после отключения или смены роли теряет доступ при следующем запросе. Заголовки роли и автора от браузера не пересылаются.

## Денежный протокол

```mermaid
sequenceDiagram
    participant B as Браузер
    participant C as Payment Core
    participant P as Платформа
    B->>C: команда + исходный Idempotency-Key
    C->>C: права, формат, комиссия; сохранить стабильную попытку
    C->>P: точные параметры попытки, без денежных блокировок
    P-->>C: ALLOW / DENY
    alt DENY
      C->>C: окончательный отказ + outbox, одна транзакция
      C-->>B: 409 RISK_REJECTED
    else ALLOW
      C->>C: повтор прав и условий; блокировки счетов; проверка TTL
      C->>C: проводки + результат + outbox, одна транзакция
      C-->>B: 201 или прежняя бизнес-ошибка
    end
```

Стабильный UUID хранится в `risk_command_attempt`, уникальность по `(actor_id, idempotency_key)` сохранена. Блокировка ключа общая с прежним `command_result`, поэтому ключ нельзя одновременно применить к другой денежной команде. Старые успешные результаты воспроизводятся без новой оценки. После сохранения валидной риск-попытки ключ связан с её параметрами; другая команда получает `IDEMPOTENCY_CONFLICT`, включая повтор после технической ошибки.

Недостаток средств, изменившаяся комиссия и прочие прежние бизнес-ошибки не становятся сохранёнными окончательными результатами. Например, после недостатка средств можно пополнить кошелёк и повторить **тот же ключ с теми же параметрами**. Проверка не разрешает молча изменить параметры сохранённой попытки. Отказ риска окончателен и воспроизводится независимо от доступности платформы и текущих правил. Текущие права проверяются и при воспроизведении.

HTTP ограничен одной секундой, размер ответа — 16 КиБ, перенаправления отключены. Проверяются идентификаторы, SHA-256 канонического серверного DTO, структура ответа и срок разрешения. Доверенная дата регистрации читается из БД ядра. В запрос не попадают пользовательские оценки или заголовки роли. При 401, таймауте, повреждённом/слишком большом ответе — `503 RISK_UNAVAILABLE` без списания; исходная попытка остаётся для повтора.

После получения денежных блокировок разрешение проверяется повторно. Истечение вызывает полный rollback и новую оценку вне транзакции; допускается до трёх циклов, затем 503. Текущая попытка не увеличивает счётчики повторно. Внутри денежной транзакции нет HTTP. Успешное проведение, сохранённый результат и событие фиксируются вместе. Отказ списания резерва оставляет его ACTIVE; отмена/истечение доступны при недоступном антифроде.

Браузер ядра сохраняет ключ и тело в `sessionStorage`, в том числе при `RISK_UNAVAILABLE`, потере ответа и перезагрузке вкладки. «Проверить результат» использует исходный запрос. После окончательного `RISK_REJECTED` можно создать новую команду с новым ключом. Закрытие вкладки прекращает сохранность `sessionStorage`; перед новой командой проверяйте историю.

## События и восстановление

Миграция V7 ядра добавляет попытки и событие `RISK_REJECTED` без денежной операции. Оно создаётся вместе с окончательным отказом и содержит исходную нормализованную команду и ID решения. Для новых POSTED-событий расходных команд сохраняются `attempt_id` и `decision_id`; исторические события не переписываются.

Экспорт включает оба вида событий. Сохранённое имя курсора `after_operation_id` / `next_after_operation_id` теперь обозначает UUID объекта: операции для POSTED либо попытки для отказа. Существующие экспорты остаются читаемыми. Импорт использует единый обработчик; отказ попадает в inbox, но не создаёт движение в `operation_view`. Повторное построение витрины не удаляет расследования и аудит.

Отказ с отсутствующим исходным решением или отличающейся командой не подтверждается получателем. Outbox сохраняется для повторной доставки; после восстановления БД нужны согласованные точки восстановления обоих сервисов. Автоматического исправления денег нет.

## Работа аналитика

Сводка показывает попытки, отказы, проведённые операции и незакрытые расследования. Поиск принимает UUID попытки, операции, участника или кошелька; доступны фильтры решения, типа команды, исходного кошелька и периода `[с, до)`, страницы по 20 записей. При загрузке и ошибке старый результат скрывается, повтор явный.

Карточка содержит точные сумму/комиссию, участников, историю оценок, версию правил, использованные факты, подтверждённые события ядра и до 20 последних операций исходного кошелька. ALLOW без события не считается успешным платежом. Отсутствие события после бизнес-ошибки ядра отображается как неизвестный денежный результат, а не выдуманный успех или отказ.

На окончательный DENY платформа создаёт одно расследование по ID попытки в той же транзакции, даже если ответ потерялся или событие ядра ещё в пути. Миграция V3 создаёт расследования для прежних DENY. Это не утверждение о списании: подтверждение результата ядра показывается отдельно.

Статусы: OPEN, IN_REVIEW, CLOSED. При CLOSED обязателен вывод SUSPICIOUS, LEGITIMATE либо INSUFFICIENT_DATA. Можно повторно открыть расследование с комментарием. Каждое сохранение требует текущую версию и непустой комментарий до 2000 символов. При конфликте версий форма предлагает обновить карточку. История сохраняет UUID автора из шлюза, время, статус, вывод и комментарий. SUSPICIOUS — оценка аналитика, а не подтверждённое мошенничество; изменение расследования не меняет исторический DENY и не возобновляет команду.

Контракт: [analyst-v1.yaml](openapi/analyst-v1.yaml), [внутренние события и риск](openapi/internal-v1.yaml). Прямые браузерные предметные API платформы закрыты, ИИ не подключён.

## Проверки

`gradlew.bat build` платформы выполняет backend, PostgreSQL и frontend-проверки. В ядре — его `gradlew.bat test`, frontend-тесты и сборка. `npm run test:e2e` платформы проверяет фильтры при ошибке, закрытие с CSRF, мобильный экран и страницу состояния. Тестовый разрешающий адаптер существует только в тестовых исходниках ядра; готовый production JAR его не содержит.

`node scripts/integration-smoke.mjs` проверяет два готовых JAR с настоящим антифродом: ALLOW, DENY, сохранённые повторы/перезапуск, отсутствие проводок при отказе, шлюз ADMIN, изменение расследования, отзыв роли, CSRF, отказ capture, отмену/возврат при остановленной платформе, повтор после восстановления и импорт обоих видов событий со сверкой. Chromium затем входит через настоящую сессию ядра, открывает кабинет и повторно открывает расследование, читает причины риска и проверяет узкую ширину. Нужны зависимости `web` и установленный Chromium, как для Playwright. Только временные БД, отдельные роли и принадлежащий скрипту контейнер; пользовательские `.env` и volumes не используются. Фактические результаты — в [progress.md](progress.md).

Нагрузочные цели, полный стенд на 8 ГБ и восстановление из внешних резервных копий относятся к отдельным испытаниям этапа 8. ИИ-агент — этап 7.
