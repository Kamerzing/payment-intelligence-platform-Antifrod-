# Архитектурные решения

## ADR-001. Отдельный сервис и модульный монолит

Приложение `payment-intelligence-platform`, group `com.kamerzing`, корневой Java-пакет `com.kamerzing.payment_intelligence`. Предметные области: integration, transactions, risk, investigations, ai, audit; инфраструктура — common и config. Пакеты будущих областей содержат описание назначения, без фиктивной функциональности.

Payment Core сохраняет свои исходники, БД, API и денежную ответственность. Общие таблицы, прямое чтение финансовой БД и межбазовые FK не допускаются. В стартовом локальном окружении PostgreSQL платформы — отдельный контейнер и volume на порту 5435; это не затрагивает контейнеры ядра.

## ADR-002. Стек и сборка

Основа версий взята из manifest-файлов выбранного Java-ядра, без его обновления: Java 21, Spring Boot 4.1.2, Gradle 9.8.2, PostgreSQL 18.6-alpine. JDBC и Flyway; версии Spring, JDBC, Flyway и JUnit управляются BOM. Frontend закреплён package-lock.json; Node.js 24.

`test` проверяет HTTP/security без Docker и без npm. `integrationTest` содержит tag integration и реальный PostgreSQL Testcontainers. `check` включает обе группы и frontend-тесты. `bootJar` зависит от webBuild и добавляет dist непосредственно в BOOT-INF/classes/static; `classes`, `test` и `bootRun` не зависят от webBuild. Так backend-разработка не требует лишнего Node-процесса.

## ADR-003. Профили и конфигурация

Без локального профиля параметры БД передаются через `PIP_DB_URL`, `PIP_DB_USER`, `PIP_DB_PASSWORD`. Профиль local-lite импортирует необязательный `.env`, использует локальную БД и открывает Swagger на loopback. В test-integration нет импорта .env, соединение выдаёт ServiceConnection. Публичный server-профиль и серверный Compose ещё не реализованы.

Системная Java и общие настройки WSL не меняются. Gradle/IDEA явно используют JDK 21. Тайны не имеют рабочих значений по умолчанию; init-local генерирует пароль, не печатая его и не перезаписывая файл.

## ADR-004. Защита стартовой версии

Публичны GET страницы, assets, status и минимальные health endpoints; документация разрешена только в local-lite без server. Остальные запросы denyAll, даже при наличии principal. Нет локальной login-формы, HTTP Basic и случайного рабочего пользователя. CSRF остаётся включённым; неизвестный изменяющий запрос без токена получает 403.

Стартовый сервис не принимает браузерную авторизацию. Будущая сессия и CSRF останутся в ядре; gateway и межсервисная аутентификация добавляются вместе с интеграцией. Не считать нынешнюю локальную страницу кабинетом ADMIN. Встроенная панель получает CSP без внешних шрифтов, скриптов и запросов.

На этапах 3–4 добавлена отдельная цепочка аутентификации внутренних машинных маршрутов; её текущее поведение описано в ADR-006. Ограничения браузерных API сохраняются.

## ADR-005. Ошибки и состояние

Ошибка содержит status, code, message, request_id, timestamp. Каждому запросу назначается серверный UUID в X-Request-ID и MDC; входящий идентификатор не считается доверенным. Ответы не содержат стек, SQL и секреты. Ошибки MVC и Security используют общий формат.

Полные стеки и сообщения объектов исключений исключены из ECS; обычный local-lite журнал использует `%nopex`. Сохраняются уровень, диагностическое сообщение, тип исключения и request_id. Прикладной код не журналирует входные данные и сообщения исключений. Настройки основаны на [документации Spring Boot](https://docs.spring.io/spring-boot/reference/features/logging.html); отсутствие приватного сообщения в ECS проверяется интеграционным тестом.

Status подтверждает только работу HTTP и явно показывает неготовые возможности. Readiness включает БД, liveness от БД не зависит. Детали health наружу не выдаются. Панель загружает status/readiness независимо, ограничивает ожидание шестью секундами и сбрасывает старое состояние перед повтором.

## ADR-006. События и риск, этапы 3–4

Outbox создаётся триггером ядра при POSTED в денежной транзакции. Отправитель сохраняет аренду отдельной короткой транзакцией, затем выполняет HTTP. Транзакционный счётчик задаёт порядок commit для материализованного экспорта REPEATABLE READ. PostgreSQL-последовательность сама по себе не дала бы такого порядка. Основание для согласованности снимка: [PostgreSQL 18](https://www.postgresql.org/docs/18/transaction-iso.html).

Получатель сохраняет неизменяемый inbox и условно обновляет operation_view по версии. Импорт использует тот же обработчик, сохраняет checkpoint вместе со страницей. Повторное построение витрины сериализуется с приёмом событий через разделяемую/исключительную блокировку источника. Прямых обращений платформы к финансовой БД нет.

Счётчики риска читают собственную таблицу risk_attempt под строковой блокировкой кошелька. Блокировка ID попытки защищает конфликтующие повторы, назвавшие разные кошельки. Версия конфигурации и использованные факты сохраняются; история неизменяема. ALLOW с TTL 1 секунда переоценивается при истечении или изменении версии правил без повторного учёта попытки. Время приводится к микросекундам PostgreSQL. Сохранённый DENY окончателен.

Отдельная SecurityFilterChain для `/internal/**` проверяет bearer-секрет и не использует браузерные сессии; CSRF не применяется только к этим машинным маршрутам. Остальные маршруты сохраняют прежние ограничения и CSRF. Такой выбор цепочки описан в [Spring Security](https://docs.spring.io/spring-security/reference/servlet/architecture.html). Отсутствующий секрет закрывает API, а не создаёт демонстрационный доступ.

Метрики `pip.risk.duration`, `pip.risk.evaluations` и `pip.integration.events` используют только ограниченный набор значений `result`; идентификаторов пользователей в labels нет. Публичный `/actuator/metrics` не открыт. Это внутренняя инструментализация, а не подтверждение целевых задержек.

Подробный протокол событий: [integration.md](integration.md). Проверка расходных команд и кабинет этапов 5–6 описаны ниже; ИИ остаётся отдельным будущим этапом.

## ADR-007. Денежная проверка и шлюз аналитика

В ядре сохранённая риск-попытка отделена от прежнего успешного command_result. Область ключа остаётся `(actor_id, idempotency_key)`; общая транзакционная advisory-блокировка сериализует все денежные команды этого ключа. Подготовка фиксирует UUID и нормализованный контекст отдельной транзакцией. Затем HTTP выполняется без открытой денежной транзакции. После ответа отдельная транзакция повторяет права/условия и проверяет TTL после денежных блокировок. Истечение откатывает деньги, результат и outbox перед новой оценкой. Старый окончательный успех воспроизводится без риска; окончательный DENY сохраняется вместе с событием, технический сбой допускает повтор.

Outbox V7 различает POSTED и RISK_REJECTED. Экспорт/импорт сохраняют общий курсор потока; идентификатором отказа служит UUID попытки. Витрина движений содержит только POSTED. В платформе V3 открывает одно расследование на DENY в транзакции решения, в том числе для прежней истории при миграции. Подтверждённый исход ядра остаётся отдельным фактом.

Шлюз ядра обслуживает `/intelligence/` и ограниченный `/api/v1/admin/intelligence/**`. Текущего включённого ADMIN он проверяет в БД при каждом запросе. Cookie и CSRF остаются на origin ядра. Только шлюз добавляет отдельный bearer и UUID автора; браузерные заголовки контекста не пересылаются. Платформа не получает паролей и сессий ядра, не обращается к его таблицам. Контроллеры делегируют доступ и HTTP отдельному сервису; разрешены только перечисленные маршруты и loopback.

Расследования используют optimistic version, обязательный вывод для CLOSED и неизменяемую историю с автором/временем. Поиск, страница и её total читаются согласованно в REPEATABLE READ. Ошибка или смена фильтров скрывает старые данные сразу. Никаких автоматических денежных действий из расследований нет. Детали запуска, семантика прежних бизнес-ошибок и ограничения: [stages-5-6.md](stages-5-6.md).

## ADR-008. Ограниченный локальный ИИ и воспроизводимый пилот

Задания ИИ сохраняются в собственной PostgreSQL, вне RiskService и денежного пути. V4 хранит неизменяемые исходные факты и завершённые отчёты; unique автора/ключа и частичный unique активной попытки защищают повторы. Очередь ограничена под общей транзакционной блокировкой, воркер — отдельной сессионной advisory-блокировкой без открытой транзакции на время HTTP. Потерянная аренда не запускает скрытый повтор модели: остаётся объяснение по правилам.

Факты читаются из согласованного снимка конкретной попытки тремя разрешёнными инструментами. Перед каждым вызовом и публикацией Core проверяет актуального ADMIN через отдельный машинный маршрут по секрету аналитика. Строки комментариев не включаются в контекст. Модель выбирает факты и рекомендации из каталога; сервер проверяет схему, обязательные свидетельства и разрешённые ссылки, формирует русский текст из подтверждённых значений. Такой подход намеренно ограничивает свободу текста для проверяемой фактической корректности. Это не обученная антифрод-модель.

Ollama запускается отдельным процессом на loopback с отключённым облаком, одним параллельным запросом и выгрузкой модели. Backend использует только фиксированный локальный тег, закреплённый digest/runtime, ограниченные HTTP-ответы и JSON-схему через `format`. Основания: [Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs), [локальный режим](https://docs.ollama.com/faq#how-do-i-disable-ollamas-cloud-features). Модель не получает SQL, shell, свободный HTTP или денежные API.

Пилотный runner создаёт только свой временный PostgreSQL, раздельные БД/роли и случайные секреты. Перед парой custom archive дампов останавливает оба backend, восстанавливает в новые БД, сравнивает все строки предметных таблиц и запускает настоящие JAR со сверкой/повторами. Измерения задержек и ресурсов сохраняются отдельно от функциональных проверок. Процедура и ограничения: [stages-7-8.md](stages-7-8.md).
