# Локальный ИИ и испытание пилота

Платформа остаётся учебной системой с тестовыми средствами. ИИ объясняет сохранённое решение правил; он не пересчитывает риск, не проводит деньги и не меняет расследование автоматически. Для первого запуска сервисов используйте [этапы 5–6](stages-5-6.md).

## Запуск модели на Windows

Нужны установленный Ollama и около 3 ГБ места под модель. В отдельном терминале из корня платформы:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/start-ollama.ps1
```

Скрипт запускает отдельный runtime на `127.0.0.1:11435`, задаёт `OLLAMA_NO_CLOUD=1`, один запрос одновременно, одну загруженную модель, очередь runtime из одного запроса, контекст 4096 и выгрузку модели после генерации. Он не меняет системное окружение и настройки другого запущенного Ollama. Не подменяйте этот процесс runtime с облачными функциями. Отключение облака описано в [официальной документации](https://docs.ollama.com/faq#how-do-i-disable-ollamas-cloud-features).

В другом терминале один раз загрузите модель и сохраните её идентичность:

```powershell
$env:OLLAMA_HOST='127.0.0.1:11435'
ollama pull qwen3:4b-instruct
node scripts/prepare-ai.mjs
```

`prepare-ai` читает только локальные метаданные, проверяет семейство, Q4_K_M и лицензию Apache, создаёт `.env.ai` без перезаписи существующего файла. Генерация остаётся выключенной. Проверенная исходная версия находится в [ai-model-lock.json](ai-model-lock.json): полный digest, runtime, лицензия и параметры. После обновления Ollama/тега явно повторите проверку совместимости и закрепление; backend отказывается использовать несовпадающую идентичность.

Профиль `local-lite` читает `.env.ai`. Запустите собранную платформу с явным включением:

```powershell
$env:JAVA_HOME='C:\Program Files\Java\jdk-21.0.12.1'
$env:PATH=$env:JAVA_HOME+'\bin;'+$env:PATH
$env:PIP_AI_ENABLED='true'
java -Xmx384m -jar build/libs/payment-intelligence-platform.jar --spring.profiles.active=local-lite
```

Core должен быть запущен по адресу `PIP_CORE_URL` (по умолчанию `http://127.0.0.1:8080`). Оба сервиса используют прежний отдельный `PIP_ANALYST_TOKEN`. Это позволяет проверять актуальные права ADMIN перед каждым чтением инструмента и перед публикацией результата; недоступность этой проверки останавливает генерацию.

Войдите ADMIN в Core, откройте `/intelligence/`, выберите попытку и нажмите «Запросить ИИ-анализ». Отчёты доступны также для ALLOW; отсутствие события проведения явно остаётся неизвестным исходом. Статусы: `QUEUED`, `RUNNING`, `SUCCEEDED`, `FALLBACK`. При выключенной/недоступной модели показывается **объяснение по правилам**, с явным указанием, что ИИ не сформировал отчёт.

## Как проверяется отчёт

Используется ограниченный рабочий процесс из трёх инструментов: `read_attempt`, `read_rules`, `read_operations`. Они читают только сохранённый снимок конкретной попытки; произвольных аргументов SQL, URL, shell и денежных действий нет. Комментарии аналитика и пользовательские тексты не передаются модели. У каждого инструмента проверяются область попытки и актуальный ADMIN через внутренний API Core; browser cookie и пароль не пересылаются.

Модель выбирает идентификаторы подтверждающих фактов и рекомендации из закрытого каталога. JSON-схема создаётся под конкретный снимок. Backend отдельно проверяет точный набор полей, типы, допустимые ссылки, отсутствие дублей, наличие всех сработавших правил и трёх обязательных ограничений. Свободный текст с новыми суммами, участниками или выводом о доказанном мошенничестве не принимается. Русский текст фактов берётся из серверного каталога. Это ограниченное объяснение с участием модели, а не свободный чат или автоматический следователь.

Сохраняются автор, время, исходный снимок, модель/digest/runtime, hash лицензии и фактов, версия шаблона, параметры, вызванные инструменты и проверенный выбор модели. Скрытые рассуждения и непроверенный ответ не сохраняются. Завершённый отчёт неизменяем. Существующие решения риска не переписываются.

Очередь PostgreSQL вмещает восемь активных заданий. На одну попытку допускается одно активное задание; новый ключ в это время получает `409 AI_ALREADY_RUNNING`. Ключ запроса UUID уникален для автора, повтор исходного ключа воспроизводит задание; изменение попытки с тем же ключом даёт конфликт. При заполненной очереди — `429 AI_QUEUE_FULL`. UI сохраняет ключ при неопределённом результате отправки в пределах открытой карточки. Перезагрузка карточки сначала загружает историю; завершённые отчёты сохраняются независимо от браузера.

Сессионная advisory-блокировка БД разрешает одному воркеру выполнять генерацию; транзакция БД во время HTTP к модели не удерживается. Таймаут генерации — 180 секунд, preflight ограничен отдельными короткими таймаутами. Максимум ответа HTTP — 32 КБ, выход — 512 токенов. Модель использует два CPU-потока и batch 128 для экономного режима. После аварийного завершения RUNNING с истёкшей пятиминутной арендой становится `FALLBACK/INTERRUPTED`, без скрытой повторной генерации. Выключенный воркер завершает ожидающие задания объяснением по правилам. Факты ограничены пятью связанными операциями, история UI — десятью последними отчётами.

## Воспроизводимое испытание

Сначала выполните полную сборку обоих проектов и установите Chromium для Playwright. Не запускайте одновременно сборки и модель на 8 ГБ RAM.

```powershell
node scripts/integration-smoke.mjs --pilot
node scripts/integration-smoke.mjs --pilot --real-ai
```

Первая команда не требует запущенной модели: проверяет контролируемый сетевой сбой и объяснение по правилам. Вторая дополнительно использует настоящий runtime на 11435 с идентичностью из `ai-model-lock.json`. Тестовые секреты создаются в памяти. Не требуется читать рабочие `.env`. Порты назначаются автоматически, PostgreSQL — отдельный контейнер с label владения и tmpfs. Удаляется только контейнер этого прогона.

После прежних сквозных сценариев выполняются 100 HTTP-запросов риска с открытым поступлением 5/с, конкурентные уникальные попытки и повторы, замер доставки, CSRF и повтор анализа, проверка 20 запросов риска при 5/с во время генерации. p95 рассчитывается по 95-му элементу отсортированных 100 результатов, для малого параллельного прогона — по 19-му из 20. Само наличие теста не подтверждает достижение цели; численные результаты сохраняются в `pilot-measurements.json`, итог — в `result.json`. Функциональные проверки, цели local-lite без генерации и цели одновременного стенда отражаются разными полями: `functional_passed`, `local_lite_targets_met`, `full_stand_targets_met`.

При недостижении выбранных измеряемых целей runner записывает `passed=false` и возвращает ненулевой код после завершения остальных проверок и очистки. С флагом `--real-ai` учитывается также p95 параллельного замера. Итоговый технический отчёт не является автоматическим допуском реальных пользователей или средств.

Оба backend останавливаются перед согласованной парой `pg_dump -Fc`. Дампы восстанавливаются одной транзакцией в отдельные пустые БД, исходные БД сохраняются. Для денег, резервов, ключей, outbox, решений, витрины, расследований, аудита и ИИ сравниваются количество и hash всех строк. Перед открытием доступа восстановленные сессии удаляются. Затем настоящие JAR запускаются на восстановленных БД: прежняя cookie получает 401, новый вход проходит, проверяются сверка и повторы прежнего успеха и DENY. Это локальная тренировка восстановления. Она не заменяет внешнее зашифрованное хранилище, расписание копий и организационный допуск пользователей.

Снимки свободной RAM и памяти JVM относятся к конкретному прогону; они не являются измерением пикового потребления. IDE, Docker, браузер и другие процессы влияют на результат. Полный рабочий день и длительная нагрузка требуют отдельного наблюдения. Результаты и остаточные ограничения см. в [progress.md](progress.md).
