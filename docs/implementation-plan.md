# План создания Payment Intelligence Platform

## Стек и стартовый объём

Java 21, Spring Boot 4.1.2, Gradle 9.8.2 / Kotlin DSL / Wrapper, PostgreSQL 18.6, JDBC и Flyway; React 19.3.1, TypeScript 7.0.2, Vite 8.3.5, Node.js 24. OpenAPI/springdoc 3.2.0; JUnit, Testcontainers, Vitest 5.0.5 и Playwright 1.64.1. Инфраструктура — Docker Compose, Git и GitHub Actions. ИИ — локальный Ollama, исходная модель Qwen3 4B Instruct Q4.

Разработка начинается с документации и запускаемого каркаса (этапы 1–2). Следующие этапы выполняются отдельными задачами. Статус проверок хранится в [progress.md](progress.md), ресурсные требования — в [workstation.md](workstation.md).

Реализация этапа 7 и воспроизводимое локальное испытание этапа 8 описаны в [stages-7-8.md](stages-7-8.md). Задания ИИ сохраняются отдельно от денежных решений; при сбое остаётся объяснение правил. Пилотный runner проверяет два JAR, браузер, настоящую модель по отдельному флагу, нагрузку и восстановление. Организационный запуск закрытой группы и длительная эксплуатация не подтверждаются одним техническим прогоном.

| Этап | Работы | Приёмка |
| --- | --- | --- |
| 1. Спецификация и окружение | Требования, архитектура, стек, ресурсы, исходная проверка ядра и инструментов; отдельный замер модели | Документы согласованы; выполненные и недоступные проверки различаются |
| 2. Заготовка проекта | Backend, собственная БД и миграция, React-страница состояния, local-lite, IDEA и CI | Сборка, HTTP/security, реальная PostgreSQL, UI и инструкции проверены |
| 3. События и витрина | Outbox ядра, доставка HTTP, дедупликация, события вне порядка, согласованный импорт истории | Перезапуск и повтор не теряют события и не дублируют результаты |
| 4. Антифрод | Версионированные правила, атомарные счётчики, объяснимые причины, генератор сценариев | Решения воспроизводимы, границы и конкурентность проверены |
| 5. Проверка до списания | Переводы, выводы, списание резервов; идемпотентность, сохранённые отказы и технические сбои | DENY/сбой не списывают деньги; повтор исходного ключа безопасен |
| 6. Кабинет аналитика | Поиск, карточки, очередь расследований, разметка, история действий | ADMIN проходит полный сценарий; USER и чужие данные защищены |
| 7. ИИ-агент | Локальные инструменты чтения, факты, JSON-схема, рекомендации и fallback по правилам | Нет выдуманных фактов; сбой модели не влияет на денежные решения |
| 8. Закрытый пилот | Сквозные, конкурентные и нагрузочные проверки, резервная копия, восстановление, демонстрация | Пройдены критерии приёмки, измерены ресурсы и зафиксированы ограничения |

## Контракты и инварианты

- Payment Core — единственный владелец денег, проводок, комиссий и резервов; платформа имеет собственную БД и обращается к ядру через API/события.
- `POST /internal/v1/risk/evaluations` реализован на этапе 4 и подключён в ядре на этапе 5: стабильный ID попытки, нормализованные параметры команды, решение `ALLOW`/`DENY`, оценка, причины, версия правил и срок разрешения. Доступ только по отдельному межсервисному секрету. Кабинет этапа 6 использует отдельный секрет шлюза и актуальные права ADMIN.
- Риск оценивается вне транзакции с блокировками денежных счетов. Решение связано с точными параметрами; незавершённая попытка не использует устаревшее разрешение.
- Окончательный отказ — `409 RISK_REJECTED`; сбой проверки — `503 RISK_UNAVAILABLE`, без списания и с возможностью повторить тот же ключ. Сохранённый результат не создаёт повторного денежного эффекта.
- Деньги — целые копейки; в JSON строки. Отказ риска не создаёт проводок. Отмена и истечение резерва доступны при сбое антифрода.
- События фиксируются атомарно с результатом команды в outbox, доставляются как минимум один раз и дедуплицируются получателем.
- В пилоте аналитик — актуальный ADMIN ядра через защищённый шлюз и общую браузерную сессию. ИИ не исполняет рекомендации и не участвует в ALLOW/DENY.

## Начальные правила пилота

| Правило | Баллы |
| --- | ---: |
| Сумма от 100 000 ₽ | 70 |
| Пятая и последующая уникальная расходная попытка за 60 секунд | 80 |
| Три и более разных получателя за 10 минут | 40 |
| Возраст пользователя менее 24 часов и сумма от 25 000 ₽ | 30 |

Сумма баллов ограничена 100; DENY начинается с 70. Это тестовые стартовые настройки, не вероятность мошенничества. Счётчики учитывают текущие уникальные валидные попытки, включая отказы риска, и защищены БД от конкурентного обхода.

## Испытания и последующее развитие

Обязательны денежные инварианты и сверка, повторы, потеря ответа, перезапуски, конкурентность, outage антифрода/модели, доставка событий, права, CSRF, восстановление и проверка фактов ИИ.

Начальные цели: p95 оценки риска до 200 мс при 5 запросах/с, таймаут обращения 1 секунда, доставка события до 5 секунд при исправной связи. Это цели, не подтверждённые показатели. На 8 ГБ разработка идёт в облегченном режиме; полный стенд и модель испытываются отдельно.

После пилота: настройка правил по расследованиям, ML на качественно размеченных данных, постоянный сервер. Реальные деньги и ожидание ручного разрешения операции требуют отдельной спецификации.
